# 企业版执行跟进与风险可见性 PRD

## 1. Executive Summary

- **Problem**
  企业版中的团队负责人在项目进入执行阶段后，很难低成本地看见当前项目是否健康，往往需要依赖开会、群聊追问、人工维护台账等方式获取状态，导致风险暴露过晚、执行跟进成本过高。

- **Solution**
  在企业版项目内提供一套“项目健康摘要 + 风险任务清单 + 跟进行动入口”的能力，让负责人在项目上下文中快速识别风险、查看原因并直接采取行动。

- **Expected impact**
  预期提升企业版中活跃项目的可管理性和执行跟进效率，降低负责人手工跟进成本，增强产品在团队执行场景中的留存价值。

---

## 2. Edition and Scenario Context

- **Edition：**
  Enterprise

- **Primary role：**
  团队负责人 / 项目 Owner

- **Collaborating roles：**
  - 项目成员
  - 管理者 / 观察者
  - 管理员（间接）

- **Core scenario：**
  项目已启动并处于执行阶段，负责人需要判断项目当前健康度、识别风险任务与责任人，并做出后续跟进动作。

- **Out-of-scenario boundary：**
  - 不解决项目创建与启动问题
  - 不解决复杂跨项目组合管理问题
  - 不解决高级 BI / 经营报表问题
  - 不解决绩效考核体系问题

## 3. Problem Statement

### Who has the problem

企业版中的团队负责人 / 项目 Owner，尤其是需要管理多人协作、多个节点和持续推进节奏的负责人。

### What breaks today

- 项目状态分散在任务列表、群聊、会议、个人口头同步和线下表格中
- 负责人无法快速知道哪些任务存在逾期、阻塞、无负责人或关键节点风险
- 为了掌握项目真实状态，负责人需要频繁催问和手动追踪
- 管理者需要了解整体进展时，也缺少可信且低成本的项目健康信息

### Why it matters now

- 企业版当前最核心的价值主张之一就是“团队执行系统”
- 如果负责人看不见风险、无法低成本跟进，产品就会退化成记录工具
- 当前需求分析中，这类问题已表现为企业版最强的机会之一，适合优先进入方案和路线图

- **Strategic fit**
  该能力直接服务企业版“执行跟进与管理可见性”的核心价值，符合当前对企业版优先服务团队协作和执行系统场景的判断。

## 5. Solution Overview

### Summary

在项目详情页中增加“项目健康摘要”模块与“风险任务清单”，让负责人在原项目上下文中看到项目当前健康状态、主要风险来源，并直接进行跟进行动。

### Main flow

1. 负责人进入进行中的项目
2. 系统展示项目健康摘要
3. 系统列出重点风险任务
4. 负责人点击风险项查看详情
5. 负责人进行跟进行动
6. 系统记录和刷新项目状态

### Key user actions

- 查看项目健康摘要
- 查看风险任务和风险原因
- 对责任人发起提醒
- 重新分配负责人
- 调整截止时间
- 查看阻塞或逾期任务详情

### MVP shape

MVP 阶段优先提供：

- 基于规则的项目健康摘要
- 风险任务清单
- 基础跟进行动入口

不在第一阶段做：

- 复杂 AI 风险评分
- 跨项目统一驾驶舱
- 高级管理报表中心

## 6. Roles, Permissions, and Object Model

### Roles involved

- **团队负责人 / 项目 Owner**
  核心使用者，负责查看项目健康和采取跟进行动

- **项目成员**
  负责更新自己任务状态，接收提醒，被动影响项目健康结果

- **管理者 / 观察者**
  查看项目总体状态和风险，但不一定拥有任务修改权限

### Permission rules

- 项目 Owner 可查看项目全部健康摘要和风险清单
- 项目 Owner 可执行提醒、重新分配、调整时间等操作
- 项目成员仅查看与自己相关的任务和提醒，不默认拥有全局风险管理能力
- 管理者 / 观察者默认只读，不直接修改任务结构

### Affected objects

- 项目
- 任务
- 负责人
- 截止时间
- 状态
- 阻塞原因
- 提醒 / 跟进行动

### State transitions

- 任务从 `进行中` -> `已逾期`
- 任务从 `进行中` -> `被阻塞`
- 任务 `无负责人` / `无截止时间` 进入管理风险态
- 项目从 `正常` -> `关注中` -> `风险中`

### Object logic notes

- 项目健康状态不建议完全依赖手工输入
- 第一阶段应采用清晰、可解释的规则型逻辑
- 风险状态需要可追溯，避免黑盒判断

---

## 7. WPS Integration Points

- **组织 / 通讯录**
  - 用于识别负责人、成员和可提醒对象

- **消息 / 通知系统**
  - 用于承接“提醒责任人”“待跟进通知”等动作

- **日历**
  - 可作为后续增强方向，用于承接关键节点提醒

- **文档 / 会议**
  - 当前版本不作为主入口，但后续可与文档、会议形成“执行 -> 状态可见 -> 跟进”的闭环

## 8. Requirements

### User stories

#### Story 1

作为项目负责人，我希望打开项目时能立即看到项目当前健康状态和主要风险，这样我就能快速判断是否需要跟进。

**Acceptance criteria**

- 当项目状态为“进行中”时，项目详情页应展示项目健康摘要模块
- 健康摘要至少应展示：
  - 项目当前健康状态
  - 风险任务总数
  - 逾期任务数
  - 被阻塞任务数
  - 无负责人任务数
- 健康摘要中的统计数据应与当前项目任务数据一致
- 若项目当前无明显风险，应展示明确的正常状态，而不是空白或无反馈

#### Story 1.1

作为项目负责人，我希望系统给出的健康状态是可解释的，这样我才能信任它并据此采取行动。

**Acceptance criteria**

- 项目健康状态不得只显示抽象分数，必须能看到至少一类风险来源说明
- 点击健康状态或风险数字后，应可进入相应风险清单或风险详情
- 若健康状态为“关注中”或“风险中”，系统必须至少说明一项触发原因
- 第一阶段不应依赖不可解释的 AI 黑盒结论作为唯一健康判断依据

#### Story 2

作为项目负责人，我希望系统明确告诉我哪些任务逾期、阻塞、无负责人或临近关键节点，这样我能优先处理真正会影响项目的事项。

**Acceptance criteria**

- 风险清单至少应覆盖以下风险任务：
  - 逾期任务
  - 被阻塞任务
  - 无负责人任务
  - 无截止时间任务
  - 临近关键节点但未完成的任务（若项目已定义里程碑或关键节点）
- 风险清单中的每条任务至少展示：
  - 任务名称
  - 当前状态
  - 当前负责人
  - 截止时间或缺失字段提示
  - 风险原因
- 风险清单默认应按风险优先级或时间紧迫度排序，而不是随机排序

#### Story 2.1

作为项目负责人，我希望风险清单只暴露真正值得我优先处理的问题，而不是把所有异常信息平铺给我。

**Acceptance criteria**

- 已完成任务不得出现在风险清单中
- 已归档项目中的任务不得进入当前项目健康摘要计算
- 同一任务同时命中多个风险条件时，默认只展示一次，并列出多个风险原因
- 风险清单应优先暴露与项目推进直接相关的风险，而不是只展示所有数据缺失项

#### Story 2.2

作为项目成员，我希望看到自己相关任务被标记为风险的原因，这样我知道该更新什么，而不是只收到模糊提醒。

**Acceptance criteria**

- 成员在查看自己相关任务时，可见该任务的风险原因
- 若任务被标记为“阻塞”，应支持展示阻塞原因文本或来源说明
- 若任务风险来自基础信息缺失，如无负责人或无截止时间，应明确提示缺失字段
- 成员不能通过该能力看到超出自己权限范围的其他任务详情

#### Story 3

作为项目负责人，我希望看到风险后能直接发起提醒、调整负责人或修改时间，而不是再去多个页面查找和操作。

**Acceptance criteria**

- 从风险清单中的每条任务，项目负责人至少可直接执行以下动作之一：
  - 发送提醒
  - 重新分配负责人
  - 修改截止时间
  - 打开任务详情查看更多信息
- 跟进行动应保留在项目上下文中，不要求负责人跳转多个无关页面
- 触发跟进行动后，系统应明确反馈动作是否成功

#### Story 3.1

作为项目负责人，我希望系统记录我已做过的跟进行动，这样我不会重复处理同一风险。

**Acceptance criteria**

- 当负责人执行提醒、改期或重分配后，系统应记录相应动作事件
- 用户刷新页面后，相关任务的最新负责人、截止时间和状态应反映刚才的改动
- 第一阶段即使不提供完整行动历史页，也必须保留基础事件埋点和动作结果状态

#### Story 4

作为管理者 / 观察者，我希望能看到项目总体健康情况和关键风险摘要，但不需要直接修改任务内容。

**Acceptance criteria**

- 具备项目查看权限的管理者 / 观察者应可看到项目健康摘要
- 管理者 / 观察者默认只读，不可直接执行负责人级别的跟进行动
- 若权限体系限制其查看任务详情，系统至少应提供项目级健康摘要和风险数量

#### Story 5

作为产品与研发团队，我们希望项目健康判断依赖稳定、可追踪的数据规则，而不是人工口径不一致，这样后续才能持续优化这项能力。

**Acceptance criteria**

- 第一阶段项目健康状态应基于明确规则生成
- 每类风险规则应可在实现逻辑中追溯
- 埋点事件应支持后续分析：
  - 风险是否被看到
  - 风险是否被处理
  - 处理后项目状态是否改善

### Acceptance logic by module

#### A. 健康摘要模块

- 系统应在进行中项目中默认展示健康摘要
- 健康状态至少应分为三档：
  - 正常
  - 关注中
  - 风险中
- 状态档位必须能映射到清晰规则条件

#### B. 风险清单模块

- 风险清单应支持按风险原因或时间紧迫度查看
- 风险原因应使用清晰的产品语言，而不是内部字段名
- 风险项不得重复展示

#### C. 跟进行动模块

- 项目负责人必须能从风险项直接进入后续动作
- 每种动作触发后，系统都应更新对应任务或事件状态
- 若用户没有对应权限，操作入口应不可见或不可用

#### D. 角色权限模块

- 项目负责人、成员、管理者 / 观察者的可见范围必须区分
- 管理者 / 观察者在第一阶段不可通过该能力直接改动任务
- 项目成员不可看到与自己权限无关的全局管理动作入口

### Edge cases

- 成员长期不更新状态，导致健康结果失真
- 项目存在大量历史任务，稀释真实风险信号
- 项目没有建立明确里程碑或截止时间，导致健康摘要可解释性不足
- 提醒过多导致用户视为噪音
- 管理者误把健康摘要当绩效评价工具

## 9. Metrics and Instrumentation

### Primary metric

- 企业版中使用“项目健康摘要”的活跃项目数

### Guardrail metrics

- 项目负责人额外状态维护成本是否上升
- 风险提醒后的有效操作率
- 因健康摘要误判导致的用户反馈 / 反感情况

### Events to track

- `project_health_view_opened`
- `project_health_status_viewed`
- `risk_signal_clicked`
- `followup_action_triggered`
- `owner_reassigned`
- `task_due_date_updated`
- `task_blocked_marked`
- `risk_notification_sent`

### Suggested validation measures

- 负责人在项目页停留后是否发生跟进行动
- 风险视图是否比普通任务列表更能触发跟进行为
- 使用该能力的项目是否表现出更稳定的执行更新节奏

## 10. Dependencies, Risks, and Rollout

### Dependencies

- 任务状态数据质量
- 项目负责人、成员、截止时间等对象字段完整性
- 企业版消息 / 通知触达能力
- 权限体系对角色差异的支持

### Risks

- **风险 1：健康信号不可信**
  - 说明：如果规则过于粗糙，负责人会认为摘要没有参考价值
- **风险 2：提醒泛滥**
  - 说明：如果只会“多提醒”，产品会变成噪音源
- **风险 3：视图打开但不行动**
  - 说明：如果只能看，不能顺畅跟进，价值会被削弱

### Rollout plan

第一阶段建议：

1. 仅在 Enterprise 中上线
2. 先支持进行中项目
3. 先聚焦项目 Owner 视角
4. 用规则型风险信号做 MVP
5. 限定一组基础跟进行动

第二阶段再考虑：

- 主动提醒能力增强
- 管理者汇总视图
- 跨项目健康管理
- 更智能的 AI 风险识别

## 11. Out of Scope

- 复杂经营看板 / BI 报表中心
- 全局跨项目驾驶舱
- 自动绩效评价
- 全量 AI 自动推进系统
