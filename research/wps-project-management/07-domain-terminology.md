# Domain Terminology

## Purpose

这份文档用于统一产品领域术语，避免团队和 AI 在以下问题上各说各话：

- 同一个词指代不同东西
- 不同的人用不同词指代同一个对象
- 方案文档、PRD、埋点、设计稿里的术语不一致

术语一致不是文档洁癖，而是产品设计、研发实现、数据定义和跨团队沟通的基础。

---

## Usage Rules

- 优先记录产品内真实使用的词，而不是理论上更优雅的词
- 明确“推荐用词”和“避免混用词”
- 如需中英混用，写清标准写法
- 如果词语在不同上下文里含义不同，必须拆开说明

## Core Object Definitions

### Project
- 中文名称：项目
- 定义：围绕一个目标组织的一组任务、阶段和协作行为的执行容器
- 在产品中的作用：承载“从想法 → 执行 → 结果”的完整过程（核心对象）
- 生命周期 / 状态：未开始 → 进行中 → 已完成 → 已归档
- 与其他对象的关系：包含任务 / 里程碑 / 成员；由负责人驱动推进
- 常见误解：
  - ❌ 项目 = 任务集合
  - ✅ 项目 = 有目标的执行系统

### Task
- 中文名称：任务
- 定义：可被执行和完成的最小工作单元，必须有负责人
- 在产品中的作用：驱动执行推进的核心单位
- 生命周期 / 状态：待开始 → 进行中 → 已完成 → 已阻塞
- 与其他对象的关系：属于项目；可拆分为子任务；由负责人执行
- 常见误解：
  - ❌ 没有负责人的事项
  - ✅ 每个任务必须有 owner

### Subtask
- 中文名称：子任务
- 定义：对任务的进一步拆解，用于细化执行步骤
- 在产品中的作用：降低复杂任务执行难度
- 生命周期 / 状态：同 Task
- 与其他对象的关系：隶属于任务
- 常见误解：
  - ❌ 可以无限嵌套
  - ✅ 应保持轻量（1层为主）

### Milestone
- 中文名称：里程碑
- 定义：项目中的关键节点或阶段性成果标记
- 在产品中的作用：帮助用户感知进度与节奏
- 生命周期 / 状态：未达成 → 已达成
- 与其他对象的关系：关联多个任务
- 常见误解：
  - ❌ 等同任务
  - ✅ 是“节点”，不是执行单元

### Template
- 中文名称：模板
- 定义：可复用的项目或任务结构
- 在产品中的作用：加速项目创建（AI生成的一种静态替代）
- 生命周期 / 状态：创建 → 使用 → 更新
- 与其他对象的关系：用于生成项目
- 常见误解：
  - ❌ 模板必须手动配置
  - ✅ AI生成本质是动态模板

### View
- 中文名称：视图
- 定义：展示项目或任务的不同方式（列表、看板等）
- 在产品中的作用：辅助理解数据
- 生命周期 / 状态：无状态
- 与其他对象的关系：作用于项目/任务
- 常见误解：
  - ❌ 视图 = 核心能力
  - ✅ 只是展示层

### Member
- 中文名称：成员
- 定义：参与项目协作的用户
- 在产品中的作用：协作执行
- 生命周期 / 状态：加入 → 活跃 → 移除
- 与其他对象的关系：参与任务但不一定负责
- 常见误解：
  - ❌ 成员 = 负责人
  - ✅ 成员只是参与者

### Assignee
- 中文名称：负责人
- 定义：对任务结果负责的人
- 在产品中的作用：执行责任归属
- 生命周期 / 状态：分配 → 执行 → 完成
- 与其他对象的关系：绑定任务
- 常见误解：
  - ❌ 多负责人
  - ✅ 一个任务一个 owner

### Comment
- 中文名称：评论
- 定义：围绕任务/项目的上下文沟通信息
- 在产品中的作用：承载协作沟通
- 生命周期 / 状态：创建 → 回复 → 结束
- 与其他对象的关系：绑定任务/项目
- 常见误解：
  - ❌ IM聊天
  - ✅ 必须与执行对象绑定

### Reminder
- 中文名称：提醒
- 定义：推动任务执行的触发信号
- 在产品中的作用：减少“遗忘”和“拖延”
- 生命周期 / 状态：触发 → 发送 → 处理
- 与其他对象的关系：关联任务
- 常见误解：
  - ❌ 通知
  - ✅ 推动执行


### Status
- 中文名称：状态
- 定义：任务或项目的执行阶段
- 在产品中的作用：描述进度
- 生命周期 / 状态：可流转
- 与其他对象的关系：绑定任务/项目
- 常见误解：
  - ❌ 状态 = 进度
  - ✅ 状态是离散阶段

### Priority
- 中文名称：优先级
- 定义：任务重要性或紧急程度
- 在产品中的作用：辅助排序与决策
- 生命周期 / 状态：可变
- 与其他对象的关系：绑定任务
- 常见误解：
  - ❌ 优先级决定执行
  - ✅ 只是参考

## Role and Permission Terminology

如果产品涉及协作，角色和权限词汇必须统一。

- 管理员
- 创建者
- 项目负责人
- 成员
- 观察者 / 访客
- 协作者

### 管理员
- 定义：管理工作空间或团队配置的角色
- 拥有哪些关键权限：成员管理、权限配置、系统设置
- 不具备哪些权限：具体任务执行
- 容易混淆的点：不是项目负责人

### 创建者
- 定义：创建项目或任务的用户
- 拥有哪些关键权限：编辑、删除
- 不具备哪些权限：自动拥有管理权
- 容易混淆的点：不等于负责人


### 项目负责人
- 定义：对项目整体结果负责的人
- 拥有哪些关键权限：分配任务、调整项目
- 不具备哪些权限：组织级管理
- 容易混淆的点：不是管理员

### 成员
- 定义：参与项目的人
- 拥有哪些关键权限：查看、执行任务
- 不具备哪些权限：修改项目结构
- 容易混淆的点：不是负责人

### 观察者 / 访客
- 定义：只查看不参与执行的用户
- 拥有哪些关键权限：查看
- 不具备哪些权限：修改
- 容易混淆的点：不是成员

### 协作者
- 定义：临时参与某些任务的人
- 拥有哪些关键权限：有限编辑
- 不具备哪些权限：项目管理
- 容易混淆的点：不是成员

## Product Language Guidelines

写清产品和文档里的命名约束。

### 命名原则（核心规则）
1. 优先使用“用户自然语言”，而不是系统术语
2. 优先表达“结果与动作”，而不是“结构与配置”
3. 尽量使用短词（2-4字），降低认知成本
4. 避免企业软件风格（流程、节点、审批等）
5. 同一个对象，全产品只允许一个名称

### 哪些词适合给用户看
- 项目
- 任务
- 负责人
- 成员
- 进度
- 状态
- 提醒
- 评论
- 阶段（代替“流程步骤”）
- 模板
- 下一步（AI推荐）

👉 特点：
- 直观
- 口语化
- 不需要学习

### 哪些词只用于内部（研发 / 埋点 / 数据）
- workflow_app
- workflow_instance
- step_config
- execution_signal
- ai_adoption
- task_update_event
- state_transition
- escalation_event

👉 原则：
- 内部可以复杂，用户界面必须简单

### 哪些词不应该出现在用户界面中
- 流程应用
- 流程实例
- 审核项
- 节点配置
- 权限模型
- 状态流转
- 工作流
- 编排
- 表单绑定

👉 原因：
- 太“系统化”
- 太“企业软件”
- 与 WPS 用户心智不匹配

### 中英文 & 命名规范
- 前台统一使用中文（面向用户）
- 后台/API/埋点统一使用英文 snake_case
- AI相关术语统一用中文表达（避免 technical 英文）
- 不混用中英文（例如：Task任务 ❌）

### AI相关表达规范（非常关键）
推荐表达：
- “帮你生成”
- “自动整理”
- “建议下一步”
- “帮你推进”

避免表达：
- “调用模型”
- “执行推理”
- “生成结构化数据”

👉 原则：
- 用户感知的是“帮我做事”，不是“AI在工作”

## Synonyms and Forbidden Terms

| Preferred Term | Avoid / Deprecated Term | Why |

| 项目负责人 | owner / 主责人 / 管理人 | 避免混乱，统一责任语义 |
